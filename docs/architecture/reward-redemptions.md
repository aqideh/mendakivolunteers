# Reward redemptions and sponsor reconciliation

**Decision date:** 30 September 2026

## Purpose

KELUARGA may allow volunteers to exchange earned points for sponsor- or partner-funded rewards such as vouchers. Rewards are separate from badges and do not change how points are earned.

The redemption system must make three things independently auditable:

1. the volunteer's point deduction;
2. the reward/voucher that was issued or reserved;
3. the sponsor-facing record of who redeemed, when, and under which reward.

## Core model

```text
point ledger balance
  -> active reward
  -> atomic redemption transaction
     -> reward_redemptions row
     -> negative point-ledger entry
     -> voucher assignment when applicable
     -> append-only redemption audit
```

A redemption must never deduct points without creating the redemption record, and it must never issue the same voucher to two volunteers.

## Reward catalogue

A reward belongs to a sponsor/partner and stores:

- reward name and description;
- points cost;
- availability period;
- total quantity limit, where applicable;
- per-volunteer redemption limit;
- fulfilment method;
- sponsor reference;
- status: draft, active, paused or retired.

Draft, paused and retired rewards are not volunteer-visible.

The initial staging release deliberately contains no placeholder rewards because sponsor offers are still pending.

## Voucher inventory

Voucher-code rewards use a server-only voucher inventory. Voucher records store:

- voucher code;
- reward;
- sponsor reference;
- expiry;
- availability/assignment state;
- linked redemption after issue.

Unassigned voucher codes are never returned in volunteer catalogue reads or sponsor summary pages.

Assignment uses database row locking so concurrent redemptions cannot receive the same voucher.

## Atomic redemption

`core.redeem_reward` validates the authenticated volunteer, account state, current point balance, reward availability, reward limits and voucher availability in one database transaction.

Successful redemption writes:

- a canonical `reward_redemptions` row with volunteer/reward/partner snapshots;
- a negative `point_ledger_entries` adjustment using the `reward_redemption` source;
- the voucher assignment, when relevant;
- append-only audit events.

A request UUID makes retries idempotent.

## Audit trail

The immutable redemption record snapshots the data sponsors normally need for reconciliation:

- redemption ID;
- volunteer KEL ID;
- volunteer name;
- volunteer email;
- reward;
- partner;
- points cost;
- redemption time;
- current redemption status.

Voucher linkage adds voucher code, sponsor reference and expiry.

Lifecycle changes append to `reward_redemption_audit`. They do not rewrite historical audit events.

Sponsor CSV exports are themselves recorded in `reward_partner_report_exports` with the generating staff user, filter parameters, time and row count.

## Sponsor / partner access

Phase 1 uses a sponsor-filtered CSV generated by authorised MENDAKI Volunteer Team/Admin users. This is the safest initial sharing model because sponsor identities and access arrangements are not confirmed yet.

When recurring sponsor access is required, add a separate partner identity/access layer rather than reusing MENDAKI staff roles. Partner users should be scoped to one or more partner IDs and receive read-only access to only their partner's redemption projection.

Recommended partner portal fields:

- redemption ID;
- reward;
- redeemed at;
- fulfilment status;
- volunteer KEL ID;
- volunteer name;
- volunteer email only where required for fulfilment;
- voucher/reference identifier;
- aggregate redeemed / issued / remaining counts.

Do not expose volunteer profiles, points histories, other partners, staff metadata, or unrelated KELUARGA data.

## Status model

Current redemption statuses:

- `pending_fulfilment` — points deducted, manual fulfilment still required;
- `issued` — voucher/reward has been issued;
- `cancelled` — redemption cancelled without representing a completed fulfilment;
- `refunded` — points have been restored via a new positive point-ledger entry.

Refunds must be compensating ledger entries. Existing point entries are never edited or deleted.

## Operating process

Before an offer goes live:

1. create the partner;
2. create the reward as draft;
3. confirm points cost, quantity, per-person limit, validity and terms;
4. import/record voucher inventory if codes are supplied;
5. reconcile voucher count to sponsor-provided inventory;
6. activate the reward;
7. test one staging redemption and one duplicate/concurrent redemption case;
8. confirm sponsor CSV fields and data-sharing basis.

During a campaign, Volunteer Management should reconcile active redemptions and voucher inventory with the sponsor on an agreed cadence.

At campaign close, pause/retire the reward, reconcile final issued/unused/void inventory, retain the redemption/audit trail, and document any refunds or corrections as new audit/ledger entries.
